# Requirements: Dependency Upgrade Assistant 2.0

## Intent
Transform the existing Dependency Upgrade Assistant prototype into an interactive, security-first developer platform for Python repositories. The platform empowers developers to deterministically analyze dependency health, evaluate candidate version upgrade paths, assess breaking changes and compatibility risks with advisory AI assistance, inspect source-code usage via AST parsing, approve explicit modifications with human control, validate changes inside isolated Docker execution environments, and export cryptographically verified deliverables.

The initial release operates strictly as a local-first platform (React, FastAPI, SQLite, local Docker daemon, local Ollama) prioritizing zero-code-exfiltration privacy, defense-in-depth container containment, and robust local API browser security, while defining clean interface seams (Protocols/ABCs) for future hosted extensions (pluggable auth, remote runners, PostgreSQL) without introducing premature distributed infrastructure.

## Users and context
Individual software engineers and open-source contributors managing Python projects on their local workstations. The platform is used during routine dependency maintenance, security vulnerability remediation, and Python version migrations, running as a local-first desktop developer service with zero configuration.

## Functional requirements
| ID | Requirement | Acceptance criterion | Priority |
|----|-------------|----------------------|----------|
| FR-1 | Repository Acquisition & Workspace Isolation | Given a valid public or authenticated private GitHub HTTPS URL or local directory path, When the user triggers acquisition, Then the platform creates isolated read-only reference and mutable working directory workspaces without executing repository code, persisting PATs to disk, or exposing credentials in logs, CLI arguments, or URLs; invalid URLs or paths outside permitted directories are rejected with descriptive errors; PAT references are discarded immediately following the Git operation with minimal in-memory copies and zero disk persistence. | MUST |
| FR-2 | Recursive Multi-Manifest Discovery | Given an acquired repository, When manifest scanning runs, Then the system recursively discovers all `requirements.txt` variants and PEP 621/735 / Poetry `pyproject.toml` files, parsing constraints while preserving inline comments, leading whitespace, environment markers, and original newline formats. | MUST |
| FR-3 | Deterministic PyPI & Catalog Evaluation | Given discovered dependency specifications, When dependency evaluation runs, Then the engine queries the PyPI JSON API with in-memory caching (falling back to the local offline package catalog), classifies packages into Up to Date, Upgrade Available, or Preserved, and flags non-pinned or compound specifiers without calling build backends or LLMs. | MUST |
| FR-4 | Provider-Independent Advisory AI Analysis | Given an outdated dependency candidate, When AI risk analysis is invoked, Then the system queries the default local Ollama model or an explicitly authorized hosted LLM via an abstraction layer to generate structured breaking-change summaries and migration advice; if AI is unreachable or unauthorized, the system operates in deterministic-only mode without blocking or transmitting code. | MUST |
| FR-5 | AST-Based Source Code Inspection | Given an acquired repository and dependency upgrade candidates, When source code inspection is executed, Then the system performs static AST analysis to identify usages of deprecated APIs and generates proposed syntax and import adaptations without executing target code on the host. | MUST |
| FR-6 | Human Approval Gate for Modifications | Given analyzed dependencies and proposed AST improvements, When presented to the developer, Then zero modifications are written to disk until the developer explicitly approves each individual change or batch; unapproved changes are rejected without side effects. | MUST |
| FR-7 | Monaco Diff Inspection & Hunk-Level Review | Given proposed manifest or source modifications, When displayed in the Monaco Editor diff viewer, Then the user can inspect side-by-side or inline syntax-highlighted diffs, review file-level changes, read AI modification rationale, and accept or reject individual change hunks before applying. | MUST |
| FR-8 | Atomic Patch Synthesis & Revalidation | Given approved upgrade candidates and hunk selections, When modifications are applied, Then the platform synthesizes the changes into the mutable working copy; if selected hunks conflict or overlap with unselected hunks, or if working files changed since diff generation (stale patch), the platform aborts the partial application with an actionable error; upon successful synthesis, the platform runs an automated AST/syntax check to verify structural validity before validation. | MUST |
| FR-9 | Isolated Containerized Validation | Given an updated working copy, When validation is initiated, Then the system executes whitelisted verification commands (e.g. `py_compile`, `pytest`, `ruff check`) inside an ephemeral container pre-configured with required test tooling; the container runs with non-root user (`--user 1000:1000`), no network access (`--network none`), resource caps (512MB RAM, 1.0 CPU, 64 PIDs), `--security-opt=no-new-privileges`, dropped capabilities (`--cap-drop=ALL`), read-only container root (`--read-only`) with a restricted tmpfs (`--tmpfs /tmp:rw,noexec,nosuid,size=64m`), read-only reference mount (`:ro`), and forbidden Docker socket access; untrusted repository code or build scripts NEVER run on the host; if required testing tools are missing from the container, execution terminates with status `NOT_RUNNABLE` (Reason: `TOOL_MISSING`); if Docker is unreachable, validation terminates with status `NOT_RUNNABLE`. | MUST |
| FR-10 | Cryptographically Verified Artifact Export | Given a completed analysis and validation run, When the user requests export, Then the platform generates a validated unified `.patch` file, a verified `.zip` archive of the working copy with SHA-256 integrity verification, and a comprehensive Markdown report. | MUST |
| FR-11 | Decoupled Modern Frontend Interface | Given the full-stack architecture, When the user accesses the platform via browser, Then the application presents a high-density, professional developer interface (Overview Dashboard, Repository Workspace, Dependency Explorer, AI Upgrade Review, Monaco Diff Reviewer, Validation Center, and Artifact Manager) adhering to the `frontend-design` token system. | MUST |
| FR-12 | Real-Time Execution Streaming & Job Tracking | Given long-running pipeline operations (cloning, PyPI metadata fetching, AI inference, Docker validation), When a pipeline run executes, Then the backend streams stage-by-stage status, execution logs, and progress events to the client over Server-Sent Events (SSE) or WebSockets. | SHOULD |
| FR-13 | Persistent Analysis History | Given multiple repository analysis sessions, When a user revisits the platform, Then historical runs, dependency reports, validation outcomes, and generated diffs are retrievable from local persistent storage (SQLite). | SHOULD |
| FR-14 | Clean Interface Seams for Extensibility | Given the initial-release backend architecture, When internal service boundaries are established, Then storage, authentication, and execution runners are decoupled behind Python Protocols/ABCs (with concrete implementations for SQLite, NoAuth/LocalAuth, and LocalDockerRunner), without importing or deploying multi-tenant schemas, PostgreSQL drivers, Celery/Redis message brokers, or remote runners in the initial release. | SHOULD |

| ID | Requirement | Acceptance criterion | Priority |

| NFR-5 | Performance & Responsiveness | P95 API response time for cached manifest and dependency queries MUST be under 200 ms; in-memory caching of PyPI responses MUST prevent redundant external HTTP queries during a session. | MUST |
| NFR-6 | Accessibility (a11y) & Usability | The web interface MUST meet WCAG 2.1 Level AA contrast standards, provide high-contrast visible keyboard focus indicators, support full keyboard navigation, and respect `prefers-reduced-motion`. | MUST |

| NFR-8 | Observability & Audit Trail | All state machine transitions and approval gates MUST be recorded in an append-only, SHA-256 hash-chained audit log verified via `aidlc.py verify`. | MUST |

## Assumptions
- Initial release is local-first: runs on macOS and Linux with Python 3.10–3.14, local Docker daemon, SQLite database, and local Ollama instance.
- Single-user local developer mode operates with zero-configuration authentication; multi-layered local security (localhost binding, Host header validation, Origin/null-Origin rejection, Content-Type enforcement, anti-CSRF headers) protects against malicious browser contexts.
- Cloud LLM integrations (OpenAI, Anthropic, Gemini) operate under a Bring-Your-Own-Key (BYOK) model, with API keys stored in local secure configuration and used only when explicit repository-level consent is granted.
- Monaco Editor diff review focuses on side-by-side/inline comparison, explanation display, and hunk-level accept/reject; free-form in-browser file editing and line-level patch manipulation are deferred to a future milestone.
- Validation container image comes pre-configured with required testing runtimes (Python 3.11, pytest, ruff); missing container tools produce a controlled `NOT_RUNNABLE` result without running untrusted scripts on the host.
- Docker defense-in-depth flags (`--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--read-only`, `--tmpfs`) substantially mitigate container breakout risks, but do not provide an absolute mathematical guarantee against host kernel zero-day exploits or unpatched Docker daemon vulnerabilities; host kernel and Docker runtime integrity remain fundamental trust assumptions.
- Future hosted capabilities (multi-tenancy, GitHub OAuth, remote worker execution, PostgreSQL) will be implemented as modular extensions behind the established interface seams without requiring ground-up rewrites.

## Out of scope
- Arbitrary in-browser free-text file editing or manual line-by-line patch editing in the initial release.
- Multi-tenant cloud deployment, hosted worker management, Kubernetes, or Celery/Redis infrastructure in the initial release.
- Non-Python package ecosystems (Node.js/npm, Rust/Cargo, Go/Go modules) in Version 2.0.
- Automatic or unattended pushing to remote GitHub branches without explicit developer review and export action.
- Execution of untrusted setup.py, build backends, or package installer scripts on the host system.

## Open questions
- None blocking Phase 1 Inception. Architectural boundaries, security controls, and user decisions are recorded in Assumptions.

## Revision 4 — M12 Python dependency compatibility and resolution (2026-11-12)

Revision 4 adds to the earlier revisions. FR-1 to FR-21 and NFR-1 to NFR-12 stay in force, and Revision 4 rows take precedence where they overlap. Revision 3 (M11) changed only the architecture, threat model and milestone plan, so it has no requirements section here.

### Intent
A package version existing in PyPI does not establish that it works with the rest of the project. Before any Python upgrade plan can be approved, validated, applied or exported, pip's own resolver must resolve the **complete proposed dependency set** for the validation target. A trusted server-side supervisor must then independently verify the result and record it as evidence bound to the exact proposal and environment. In M12 **no third-party code executes during resolution**. Anything short of a verified successful resolution fails closed.

### New functional requirements
| ID | Requirement | Acceptance criterion | Priority |
|----|-------------|----------------------|----------|
| FR-22 | Native Python resolution of the complete proposed set, binary-only | Given a plan for a supported `requirements*.txt`, When resolution runs, Then pip (`install --dry-run --ignore-installed --only-binary=:all: --report -`) evaluates the whole proposed manifest inside the isolated resolver (FR-24). It covers PEP 440 specifiers, PEP 508 markers and extras, `Requires-Dist`, `Requires-Python` and transitive dependencies, for the validation target (CPython 3.11 on Linux, validation image digest, Docker host architecture). Resolution uses only prebuilt wheels and their metadata; no build backend, `setup.py` or package code runs. | MUST |
| FR-23 | Explicit resolution statuses | Exactly one status per resolution. **COMPATIBLE:** pip resolved the complete set and the supervisor verified it (FR-27a). **CONFLICT:** pip reports `ResolutionImpossible` among wheel-available versions and none of the involved packages has source-only releases that satisfy their constraints; the conflicting requirements are extracted. **UNSUPPORTED:** the input or the solution needs something M12 does not do: `pyproject.toml`-only projects; nested `-r`; editable, VCS, URL or local-path requirements; pip options other than `--hash` and repository-local `-c`; **a requirement satisfiable only by a source distribution** (`source_build_required`); a conflict whose resolution might depend on source-only releases; npm and other non-Python manifests (until M13). Every item is listed with a reason. **RESOLUTION_FAILED:** the resolver ran but produced no verifiable result (timeout, resource limit, blocked network, malformed or oversized report, supervisor verification failure). **RESOLVER_UNAVAILABLE:** Docker, the pinned image, the networks or the proxy are not available. **UNKNOWN:** no current evidence (never resolved, invalidated, or created before M12). | MUST |
| FR-24 | Isolated resolver execution | The resolver runs in a fresh disposable container from the pinned validation image. It runs non-root with a read-only root, all capabilities dropped, no-new-privileges, `--init`, and the NFR-13 limits. It has no host credentials, no Docker socket and no application environment. Its only mount is a read-only input directory containing the supervisor-written, sanitized manifest and constraints. It has **no writable host mount**: the report travels over stdout and is size-capped. It has no DNS and no route out except the egress proxy (FR-25). The container is destroyed after every run, including on cancel and timeout. | MUST |
| FR-25 | Controlled registry egress | Network topology: a per-job Docker `--internal` network (`dua-res-<job>`, no gateway) carries only the resolver and that job's proxy. The proxy also joins a dedicated bridge (`dua-egress`) used by nothing else. It binds only to its address on the internal network. The resolver's DNS is disabled and it reaches the proxy by IP. The proxy accepts only `CONNECT <host>:443` to `pypi.org` and `files.pythonhosted.org`; resolves DNS itself; refuses non-global addresses (loopback, RFC 1918, link-local including 169.254.169.254, CGNAT, multicast, reserved, the Docker gateway); connects to the exact address it validated (no rebinding); refuses plain HTTP, other ports and other hosts; and logs every denial (job, host, port, reason). Redirects are re-checked because each is a new `CONNECT`. The resolver, the host, the LAN, the Docker API and metadata services are unreachable except through these rules. | MUST |
| FR-26 | Constraints and version policies | `-c <file>` pointing to a file inside the repository workspace (path-contained, size-capped, free of options and URLs) is passed to pip; any other `-c` is UNSUPPORTED. **Prereleases:** pip's default; included only when a requirement explicitly pins one. **Yanked releases:** pip's default (selected only for `==` pins), and each one selected produces a warning. **Hash mode:** honoured. The policy values go into the report and the fingerprint. | MUST |
| FR-27 | Structured report, supervisor verification and fingerprint | **(a) Verification:** the supervisor treats resolver output as untrusted. It parses stdout under a size cap and strict schema, then fetches metadata itself for every selected `(name, version)` over HTTPS from PyPI: the selected wheel's PEP 658 `.metadata` file with its index-advertised hash, or else the per-version JSON API with a warning. It never downloads or opens archives and never executes code. It checks that: every selected artifact URL is on an allowed host and its hash matches PyPI's; every direct requirement and constraint is satisfied; every selected package's `Requires-Dist`, evaluated with the target-environment markers and the requested extras, is satisfied within the set; and every `Requires-Python` admits the target. Any failure is RESOLUTION_FAILED (`verification_failed`). **(b) Report:** status, ecosystem, resolver (pip version) and image digest, target runtime and platform, allow-list version, original, proposed and constraints SHA-256s, direct and transitive resolved packages with selected versions and their constraints, conflict diagnostics, unsupported items, warnings, timestamp, and fingerprint; and, per FR-32, each selected version's upload date with its source and retrieval time (or `date unavailable`) and the baseline comparison (original-resolution status, its fingerprint, and the introduced packages, or `comparison unavailable` with the reason). **(c) Fingerprint:** SHA-256 of the canonical JSON of every resolution input and environment element (ADR-011), computed only by the supervisor. Any input change produces a different fingerprint and invalidates earlier evidence. | MUST |
| FR-28 | Fail-closed enforcement | Plans and diffs are generated and displayed whatever the status, labelled "Compatibility not verified" unless COMPATIBLE. Approval is accepted only if the plan's latest evidence is COMPATIBLE and its fingerprint equals the supervisor's recomputation; every other status gets 409 `compatibility_not_verified`, with no override. Validation, workspace apply and export enforce the same check. The approval binds the resolution fingerprint alongside the M11 validation-policy fingerprint, and both are enforced. Client-supplied statuses or fingerprints are ignored. | MUST |
| FR-29 | Resolution jobs | Resolution only (not validation) runs as a background job. Each job runs two resolutions one after the other, under identical settings: first the original manifest (the FR-32 baseline), then the proposed manifest. Each run is a separate disposable container with its own NFR-13 limits. Cancel or timeout during either run ends the job and stores no evidence for the unfinished run. Creating one returns a job ID. States: QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED, TIMED_OUT, INTERRUPTED. Cancel kills the job's containers and removes its network. QUEUED or RUNNING jobs at a restart become INTERRUPTED, with no evidence stored. At most one active job per plan, run by a bounded worker pool. | MUST |
| FR-30 | Minimal UI integration | The plan stage shows compatibility status, progress with a working cancel action, resolver and target, resolved and transitive counts, conflicts, unsupported items with reasons, and warnings. Approval is disabled with the reason when not COMPATIBLE. npm plans state that npm compatibility verification is not yet supported. The approved visual design is preserved. | MUST |
| FR-31 | Backward compatibility | Plans and approvals from before M12 are UNKNOWN. They stay intact but cannot be approved, validated, applied or exported until resolved and re-approved. M11 validation-policy enforcement, request protections and retention continue unchanged. | MUST |
| FR-32 | Compatibility disclosure and resolved-set review | Given a dependency resolution, When its result is displayed or exported, Then: **(a) Disclosure:** every COMPATIBLE result states that compatibility means the complete dependency set resolves successfully. It does not mean the packages have been vetted or are safe, and DUA does not perform malware detection. **(b) Introduced packages:** packages present in the proposed resolved set but absent from the resolved set of the original manifest are highlighted. The baseline is the original manifest's complete resolved set, never its declared entries. The original resolution uses the same target Python version, platform and architecture, the same pinned resolver image, the same resolver configuration (binary-only, prerelease and yanked policy, constraints) and the same allow-listed index, and runs in the same job immediately before the proposed resolution. It gets its own evidence and its own supervisor-computed fingerprint, separate from the proposed resolution's. If the original manifest does not resolve COMPATIBLE (any other FR-23 status), the comparison is shown as `comparison unavailable` with that status as the reason, and no package is labelled introduced. The comparison is informational. Approval depends only on the proposed resolution (FR-28). **(c) Upload dates:** each selected package version shows the PyPI upload time of the exact distribution file the resolver selected. That file is identified by filename and SHA-256 in PyPI's file listing for that version: the PEP 691 JSON simple index `upload-time` (PEP 700), or else the per-version JSON API `upload_time_iso_8601`. When a version has several files, the selected file's time is used, never the earliest or latest file. The evidence records the source endpoint and the retrieval time (UTC). If the selected file cannot be matched or has no upload time, the UI and export show `date unavailable`. Dates are never estimated or taken from project pages, local cache timestamps or other metadata. **(d) Complete list:** the complete resolved dependency list (names, selected versions, direct or transitive, introduced flag, upload date or `date unavailable`) is available in the UI and included in the Markdown export, together with the disclosure in (a). OSV vulnerability-advisory integration is deferred to M13. | MUST |

### Assumptions
- Docker is available for resolution; otherwise the status is RESOLVER_UNAVAILABLE and approval is blocked.
- PyPI is the only index.
- The resolver target equals the validation target, which is also wheels-only (M11 staging). Source-only packages therefore can't be validated either, consistent with FR-23.
