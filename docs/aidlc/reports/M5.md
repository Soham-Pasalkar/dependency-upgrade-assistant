# Milestone report: M5 Sandboxed validation

## Summary
Milestone M5 delivers the sandboxed validation subsystem for executing dependency verification, syntax compilation, and test execution inside isolated, hardened Docker containers. The engine enforces dynamic non-root user execution matching the host identity (`UID > 0`) with fail-closed root fallback to non-root ownership (`1000:1000`), total capability dropping (`--cap-drop=ALL`), privilege escalation prevention (`no-new-privileges`), default network isolation (`--network none`), strict resource ceilings (512MB RAM, 1.0 CPU, 64 PIDs), read-only root filesystems, and temporary memory mounts. An ephemeral workspace snapshot manager replicates repository manifests while scrubbing secrets, `.env` files, and credentials, rejecting external symlink escapes and verifying recursive tree security invariants (0700 directory modes, zero group/world write on files). The subsystem provides reliable snapshot cleanup with permission restoration before deletion, and implements a fail-closed policy that truthfully reports `NOT_RUNNABLE` when the Docker daemon is absent or unreachable, strictly preventing untrusted code from ever running directly on the host machine.

## Post-Acceptance Security Remediation (Work Packages WP1 - WP10)

Following an independent post-acceptance security audit of M5, a targeted security and lifecycle remediation was implemented across 10 discrete work packages without expanding scope or rewriting functioning modules:

1. **WP1 — Host Filesystem Boundary Validation (`src/sandbox/workspace_boundary.py`):**
   - Implemented `validate_trusted_workspace_path` and `is_safe_relative_path`.
   - Enforces workspace containment relative to `settings.resolved_workspace_root`.
   - Strictly rejects arbitrary host paths (`/`, `/etc`, Windows drive paths `C:`, null bytes) and path traversal sequences (`../`, `..\`).
   - Neutralizes sibling-prefix directory confusion attacks (e.g. `/path/to/workspace_evil` vs `/path/to/workspace`) via `os.path.commonpath` checks with boundary path validation.
   - Removed client-controlled `workspace_path` from public `SandboxExecutionRequest`.

2. **WP2 — Server-Enforced Network Isolation & Decoupled Staging (`src/sandbox/dependency_staging.py`):**
   - Removed `network_enabled` field from `SandboxExecutionRequest` and enforced `--network none` as an immutable server-side execution policy. Added Pydantic validator rejecting any client attempt to submit `network_enabled`.
   - Implemented decoupled 2-stage model: Stage A performs isolated dependency staging with strict SSRF filtering (`is_safe_registry_url` rejecting private RFC 1918 subnets, loopback, and cloud metadata IPs `169.254.169.254`), while Stage B executes test commands strictly offline.

3. **WP3 — Mandatory Container Security Invariants (`src/sandbox/container_config.py`):**
   - Mandatory non-root user execution matching host identity (`--user $(id -u):$(id -g)` on POSIX non-root hosts, with fail-closed root fallback to `1000:1000`). Root execution inside the container is strictly prohibited fail-closed.
   - Total capability drop (`--cap-drop=ALL`) and privilege escalation prevention (`--security-opt=no-new-privileges:true`).
   - Root filesystem mounted strictly read-only (`--read-only`) with explicit ephemeral tmpfs mounts (`/tmp:rw,noexec,nosuid,size=64m`, `/workspace/scratch:rw,size=128m`).
   - Server-enforced resource ceilings (`sanitize_resource_limits`): RAM ceiling 1024m, CPU ceiling 2.0, PID limit 128, timeout 120s.
   - Strict prohibition of `--privileged`, `docker.sock`, and host namespaces (`--pid=host`, `--net=host`, `--ipc=host`).

4. **WP4 — Base Image Pinning & Integrity (`src/sandbox/image_catalog.py`):**
   - Pinned authentic multi-architecture SHA-256 digests for all approved base images:
     - `python:3.11-slim` -> `sha256:07d4824036af339fa1b6ef769cc99d9c10a141769538b52b3b597c84f7a7b535`
     - `python:3.12-slim` -> `sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b`
     - `node:20-slim` -> `sha256:2cf067cfed83d5ea958367df9f966191a942351a2df77d6f0193e162b5febfc0`
     - `node:22-slim` -> `sha256:5ec23b7c622b00547753bc6ffd78085dd868a68aeb41c8e0a1418f033e13d96d`
   - Image references are pinned during container launch (`image@sha256:...`) and digest is permanently logged in `ValidationReportResponse.image_digest`.

5. **WP5 — Workspace Snapshot Hardening, Filesystem Permissions & Recursive Verification (`src/sandbox/snapshot_manager.py`):**
   - Enhanced sensitive file scrubbing to exclude `.git`, `.env*`, `.ssh`, `.aws`, `.azure`, `.gcp`, `.kube`, `.docker`, `.npmrc`, `.pypirc`, certificates, and private keys.
   - Preserves safe dotfiles necessary for testing (`.pytest.ini`, `.ruff.toml`).
   - Hardens snapshot directory permissions to strict `0700` (`rwx------`), completely eliminating world-writable permissions (`0777`) and denying access to all other host users (`mode & 0o007 == 0`).
   - Ensures copied snapshot files strip group- and world-writable permissions, while retaining owner read/write access.
   - Enhanced `verify_snapshot_security_invariants()` to recursively audit the entire directory tree (0700 directories, zero group/world write on files, owner-readability, non-root container ownership, rejecting special files).
   - Reliable snapshot cleanup in `IsolatedSnapshot.cleanup()`: restores owner permissions bottom-up before deletion, removes with `ignore_errors=False`, verifies directory no longer exists on disk, and raises `SnapshotCleanupError` on failure while preserving state for retry.
   - Detects and rejects special files (FIFOs, named pipes, Unix domain sockets) with `SnapshotCreationError`, eliminating hangs during recursive directory replication.
   - Generates `SnapshotManifest` tracking total files and excluded entry counts. Fails closed on file copy errors.

6. **WP6 — Real-Time Atomic Cancellation & Lifecycle Management (`src/services/sandbox_service.py`):**
   - Atomic tracking of active execution states, container names, and subprocess handles (`_execution_states`, `_execution_containers`, `_execution_procs`).
   - `cancel_execution()` immediately invokes `docker rm -f <container_name>` and terminates the running subprocess handle.
   - State machine guards guarantee that late completion callbacks never overwrite terminal `CANCELLED` status.
   - Cleanup failures are logged to diagnostics and combined logs without overwriting earlier execution failures or cancellation status.

7. **WP7 — Streaming Bounded Log Output & ANSI Stripping (`src/sandbox/streaming_capture.py`):**
   - Replaced blocking `subprocess.run` with background streaming reader threads reading from non-blocking OS pipes.
   - Enforces a 512 KB memory limit; upon reaching quota, continues draining the OS pipe to prevent buffer-full pipe deadlock while truncating log output safely.
   - Strips ANSI control characters to protect frontend web consoles against log injection attacks.

8. **WP8 — Explicit Test Discovery Subsystem (`src/sandbox/test_discovery.py`):**
   - Implemented `TestDiscoveryManager` to verify the presence of actual test suites in target workspaces.
   - Python: discovers `test_*.py`, `*_test.py`, `tests/` directories, and `pytest.ini`.
   - Node.js: inspects `package.json` for test scripts; detects default npm placeholder scripts (`"echo \"Error: no test specified\" && exit 1"`).
   - Repositories without test suites truthfully report `NO_TESTS_FOUND`, preventing misleading false-positive `PASSED` results.

9. **WP9 — API Schema & Frontend Console Enhancements (`src/models/sandbox.py`, `frontend/src/`):**
   - Added `NO_TESTS_FOUND` to `ValidationStatus` enum.
   - Added `image_digest`, `test_discovery_status`, `staging_status`, `snapshot_files_count`, and `snapshot_excluded_count` to reports.
   - Updated React frontend (`SandboxValidation.tsx`) to display discovery badges, pinned digest tags, snapshot metrics, and handle `NO_TESTS_FOUND`.
   - Updated TypeScript client models and styles (`App.css`).

10. **WP10 — CI Configuration & Hardened Legacy Sandbox Cleanup (`.github/workflows/ci.yml`, `src/validation/`):**
    - Added dedicated `docker-sandbox-validation` job to GitHub Actions workflow running on Ubuntu runner with a live Docker daemon, testing pinned container pulls and isolated execution.
    - Hardened legacy `DockerSandboxManager`: assigns unique container names (`dua-legacy-*`) and executes forced termination (`docker rm -f`) upon timeout or exception in `finally:`.
    - Updated `M5_SANDBOX_ARCHITECTURE.md`, `M5_SANDBOX_THREAT_MODEL.md`, and this milestone report.

## Lens review
- **Architecture Lens:** Provider-independent `SandboxRunnerInterface` cleanly decouples execution logic from Docker daemon mechanics, enabling graceful degradation to `NOT_RUNNABLE` without blocking the developer workflow. Legacy `DockerSandboxManager` is clearly deprecated and routed through authoritative `ContainerConfigBuilder`, enforcing explicit container naming and forced cleanup upon timeout.
- **Security Lens:** Untrusted code execution is strictly prohibited on the host; container isolation enforces dropped capabilities, dynamic non-root user matching host identity (with fail-closed root fallback to 1000:1000), `--network none`, secret scrubbing from snapshots, recursive tree verification (0700 directories, zero group/world write on files), and strict `0700` filesystem permissions forbidding world-writable `0777` modes.
- **QA Lens:** Comprehensive suite of unit, integration, simulated root-fallback, and live container tests, bringing total test coverage to 537 backend and 17 frontend tests with 100% green pass rate. Live Docker tests on Linux CI verify 59 passed tests in the dedicated container validation job including real container execution and non-root snapshot mounts.
- **UX Lens:** The developer interface clearly visualizes Docker engine availability, containment specifications, command breakdown, and an expandable terminal console.
- **SRE Lens:** Resource ceilings (512MB RAM, 1.0 CPU, 64 PIDs) and a 512KB bounded log buffer protect server memory and compute against fork-bombs and runaway stdout loops.

## Known limitations
- When the Docker daemon is offline or absent on the host workstation (e.g. macOS developer machine without Docker Desktop running), the probe accurately reports `NOT_RUNNABLE` and tests are not executed. Live container execution requires a running Docker daemon.
- Single-tenant trust boundary: Protection against local symlink-swap race conditions (TOCTOU) relies on filesystem containment and permissions rather than kernel-level `openat(O_NOFOLLOW)` descriptor trees.
- Offline dependency staging scope: In M5, containers execute under strict `--network none` isolation and `DependencyStagingManager` operates offline (`status: NOT_REQUIRED`). Validation runs bytecode syntax compilation (`py_compile` / `JSON.parse`) and repository test suites that do not require external un-staged packages. Automated network download and caching of arbitrary 3rd-party binary wheels is intentionally deferred to Phase 3. Missing dependencies cause test commands to truthfully fail or report `NO_TESTS_FOUND`, and are never falsely reported as successful.
