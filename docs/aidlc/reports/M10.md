# Milestone report: M10 Repository-first backend integration and end-to-end completion

## Summary
The product now starts from a public GitHub URL. The server:
- clones the repository with a hardened, resource-bounded git process;
- discovers every `requirements*.txt`, `pyproject.toml` and `package.json`;
- analyzes each one and keeps the results server-side under a run ID.

From there:
- Recommendations and plans are built only from that server-held state.
- Approval is recorded on the server against the diff's SHA-256.
- Validation, workspace apply and export refuse unapproved, unknown, expired or mismatched plans.
- Repository validation runs against a copy of the real repository with the approved change applied.
- Host-side tools stage the proposed dependency versions without running package code, for an offline install inside the sandbox.

Other changes:
- Host, Origin, content-type and anti-forgery checks now protect the API.
- PyPI and npm lookups no longer fail for very large packages.
- The redesigned UI integrates all of this without changing its visual language.

## Post-submission audit (2026-11-12)
An independent audit before committing found and fixed:
- **Unit tests could download packages.** API tests with Docker mocked as available reached real `pip download` through staging. An autouse guard in `tests/conftest.py` now makes host-side staging fail closed in unit tests. Only tests marked `live_staging` may download.
- **No CI coverage of the new paths.** CI did not exercise staging or the offline install. I added `tests/test_docker_staging_integration.py`, covering Python install and test pass, Python test failure reported as `FAILED`, and npm `ci --offline` with the test script. It runs in the Docker job. I also added a `frontend` CI job (npm ci, tests, lint, build).
- **Silent stale versions.** The PyPI client's pre-existing offline fallback returns versions from the bundled catalog (dated 2026-10-27) with status `SUCCESS`. The UI showed these like live registry data. Such packages are now tagged "offline data" with a notice. Registry failures (not found, rate-limited, unreachable, too large, timed out) are tagged per package. The backend behaviour itself is unchanged.
- **Possible pipe deadlock.** `git clone` now runs with `--quiet`, so stderr output cannot fill the pipe while the watchdog polls.

## Lens review
- **Security:**
  - Only github.com and api.github.com over https, resolved to public IPs. Redirects are followed only on the same host.
  - git, pip and npm run with empty environments and isolated config. git uses no hooks, submodules, LFS or symlinks.
  - Byte, file and time caps are enforced while the clone and staging run. The per-file `RLIMIT_FSIZE` was verified to stop a native writer at the cap.
  - Approval is bound to the diff hash. A plan built from client-supplied recommendations (`/api/plan/generate`) can never be approved, validated or exported.
  - Execution reports must belong to the plan being exported.
  - Mutating requests need an allowed Origin, `X-DUA-Client: web` and JSON.
- **UX:** Defects found in the browser and fixed:
  - Repository validation was rejected because the sandbox boundary takes root-relative paths.
  - An empty plan read "0 changes… applies cleanly" next to "Awaiting review".
  - The npm example repository had no upgrades, so it was replaced with expressjs/cors.
  - Plan building is blocked when nothing is recommended.
- **Honesty:**
  - The UI states when nothing was executed (no Docker).
  - It shows whether dependencies were installed offline.
  - It labels pyproject.toml as review-only.
  - It says why staging was not possible: no wheel, editable or local install, a non-registry npm source, or a foreign tarball host.

## Known limitations
- **Offline catalog fallback.** When PyPI is unreachable, versions can come from the bundled catalog. They are now marked "offline data" in the UI, but recommendations built on them are not otherwise distinguished.
- **Not verified: the container side of validation.** Docker is not installed on this machine. These were never executed in a container:
  - the offline `pip install --no-index` and `npm ci --offline` steps;
  - pytest with staged packages;
  - the npm cache copy into the snapshot.

  They are covered by unit tests that capture the exact commands and mounts. Live evidence needs the GitHub Actions Docker job, which requires a push the owner has not yet authorized.
- **Wheel platform.** Python wheels are selected for the host's architecture (here aarch64), on the assumption that Docker runs containers natively. Packages without a Linux wheel are reported as not stageable; they are never built.
- **Workspace quota is a bounded soft limit.** It is enforced by a 250 ms watchdog, so it can overshoot by at most one polling interval and never by more than the 50 MB per-file cap, as documented in NFR-9.
- **Read-only file types.**
  - pyproject.toml is analyzed but not patched.
  - Requirement files that nest `-r` includes are analyzed but not staged.
- **Analysis is synchronous.** A request can take tens of seconds for large repositories; there is no streaming progress (FR-12 is deferred). The UI shows elapsed time.
- **Runs are kept, plans are not.** Runs and approvals persist in SQLite, but plans live in the in-memory registry (1 h TTL). After a restart, plans must be rebuilt; approvals of expired plans cannot be reused.
- **Live Ollama** was not exercised.
- **One lint warning remains**, in BackendStatus.

## Deviations
These existing tests were changed because FR-15, FR-16 and FR-17 deliberately change behaviour. No assertion about outcomes was removed.
- **Approval.** Tests that call validation, export or apply now first record a server approval, using `tests/approval_helpers.py` through the real RunStore:
  - `tests/test_export_api.py`
  - `tests/test_validation_api.py`
  - `tests/test_plan_api.py`

  The plan test also asserts that apply is refused (403) before approval.
- **End-to-end flow.** `tests/test_e2e_workflow_api.py` now uses the server-held run flow, and asserts that validation is refused (409) before approval.
- **Unknown proposals.** `test_validation_api.py::test_validation_execute_unknown_proposal_returns_404` still expects 404; the message match changed from "not found in registry" to "not found".
- **Registry statuses.** Three oversize tests in `tests/test_registry_clients.py` also accept the new `TOO_LARGE` status.
- **Host header.** `tests/test_recommendations_api.py`'s async client now uses a loopback base URL and the web client's headers.
- **Test client defaults.** `tests/conftest.py` sets the TestClient's default headers to what the real web client sends, and adds `testserver` to the allowed hosts in tests only.
