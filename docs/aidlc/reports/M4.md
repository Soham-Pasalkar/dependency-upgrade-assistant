# Milestone report: M4 Upgrade planning and patch generation

## Summary
Milestone M4 delivers an end-to-end, deterministic upgrade planning, surgical manifest mutation, unified diff generation, and patch integrity validation pipeline. The system receives validated recommendations from M3, analyzes dependency relationships, filters by user selections, detects conflicts, and creates a structured upgrade plan. The surgical mutation engine updates Python `requirements.txt` (preserving comments, whitespace, extras, environment markers, and directives) and Node.js `package.json` (preserving 2-space indentation, unrelated metadata, and SemVer range prefixes like `^` and `~`) without ever mutating the original input manifest. Multi-point patch verification proves standard unified diff syntax, in-memory patch applicability, mathematical reversibility, and traceability to validated recommendations, while an explicit human approval gate strictly blocks workspace modification until confirmed by the user.

Following an independent post-acceptance security review, M4 was reopened to execute a comprehensive security remediation:
- Strict server-controlled workspace containment (`WORKSPACE_ROOT` in `src/api/config.py`) forbidding arbitrary client-supplied absolute paths, directory traversal (`..`, encoded `%2e%2e`, backslashes), symlinks, and non-manifest targets.
- Server-managed `ProposalRegistry` storing generated proposals with UUID4 tokens, thread-safe TTL expiration, and single-use consumption to prevent client-side proposal forgery and tampering.
- Ground-truth recommendation provenance enforcement: rejecting unverified custom target overrides, enforcing trusted validation statuses (`VALIDATED`, `FALLBACK_DETERMINISTIC`), strictly rejecting `REJECTED_HALLUCINATION`, `REJECTED_INCOMPATIBLE`, and `SKIPPED`, and validating ecosystem matching.
- Independent server patch re-validation during mutation application, manifest freshness checking against current on-disk content, atomic temporary file replacement (`fsync` + `os.replace`), and rigorous API success semantics (`APPLIED` returned only upon verified on-disk write; `TARGET_NOT_FOUND`, `STALE_BASE_CONTENT`, `INVALID_PATH`, or `NOT_APPLIED` on failures).

## Changes
- `src/api/config.py`: Added `WORKSPACE_ROOT` setting (defaulting to `~/.dua/workspaces`) with `resolved_workspace_root` property.
- `src/models/plan.py`: Implemented Pydantic v2 schemas for upgrade planning (`PlannedUpgradeItem`, `UpgradePlanRequest`, `PatchIntegrityResult`, `UpgradeProposalResponse`, `WorkspaceApplyRequest`, `WorkspaceApplyResponse`, `ProposalStatus`, `UpgradeAction`), adding `proposal_id` to proposals and making `proposal_id` the authoritative token in `WorkspaceApplyRequest`.
- `src/models/__init__.py`: Exported planning and patch schemas.
- `src/services/proposal_registry.py`: Implemented thread-safe `ProposalRegistry` storing proposals with UUID4 keys, TTL expiration, eviction, and single-use consumption.
- `src/services/manifest_modifier.py`: Implemented non-destructive manifest mutation for `requirements.txt` (surgical regex/line replacements preserving comments, indentation, extras, markers, blank lines) and `package.json` (JSON parsing, prefix preservation, 2-space formatting).
- `src/services/patch_service.py`: Implemented standard unified diff generation with control line newlines (`lineterm="\n"`), pure-Python in-memory patch application (`apply_unified_diff`), and reverse patch generation (`reverse_unified_diff`).
- `src/core/diff_generator.py`: Updated `generate_unified_diff` to use standard control header newlines while maintaining brownfield backwards compatibility.
- `src/services/patch_validator.py`: Implemented multi-point patch integrity verification (syntactic validity, safe manifest path enforcement rejecting traversal and URL encoding, in-memory patch applicability, reversibility, traceability to validated candidates, and non-targeted dependency preservation) and added `validate_workspace_destination` for workspace boundary containment.
- `src/services/upgrade_planner.py`: Implemented `UpgradePlannerService` orchestrating candidate selection, conflict detection, downgrade prevention, proposal synthesis, `ProposalRegistry` registration, recommendation provenance checks, manifest freshness checks, atomic replacement, and human approval gate enforcement.
- `src/api/routes/plan.py`: Implemented FastAPI endpoints `POST /api/plan/generate`, `POST /api/plan/validate-patch`, and `POST /api/plan/apply` (with `/api/v1` aliases) resolving proposals via `proposal_id` and enforcing HTTP 403 when workspace mutation is requested without `approved=true`.
- `src/api/main.py`: Registered plan router under `/api` and `/api/v1`.
- `tests/test_code_inspector.py`: Annotated synthetic AST secret detection test fixtures with `# aidlc:allow-secret (synthetic test fixture for AST secret detection)` to transparently resolve scanner findings.
- `tests/test_manifest_modifier.py`: Added 12 unit tests verifying surgical mutation across both ecosystems.
- `tests/test_patch_service.py`: Added 8 unit tests verifying unified diff formatting, applicability, and reversibility.
- `tests/test_patch_validator.py`: Added 5 unit tests verifying multi-point patch integrity, path traversal rejection, and traceability.
- `tests/test_upgrade_planner.py`: Added 9 unit tests verifying planning logic, conflict detection, downgrade prevention, deterministic proposals, and human approval gate enforcement.
- `tests/test_plan_api.py`: Added 6 FastAPI integration tests verifying endpoints, status codes, and approval gate rejection.
- `tests/test_plan_security.py`: Added 19 comprehensive security tests covering path traversal attacks, symlink escapes, proposal forgery, proposal replay, arbitrary custom versions, skipped validations, stale content detection, and atomic replacements.

## Lens review
- **Architecture Lens:** Pass. Upstream interface boundary between M3 recommendations and M4 planning is cleanly decoupled via structured Pydantic schemas. Proposal storage is encapsulated in `ProposalRegistry` with TTL and single-use tokens. Manifest modification and patch validation are isolated domain services independent of FastAPI transport.
- **Security Lens:** Pass. Airtight workspace containment (`validate_workspace_destination`) prevents directory traversal, symlink escapes, absolute paths, and unauthorized file mutations. Proposal IDs generated server-side prevent client-side integrity forgery. Candidate validation status enforcement rejects hallucinated, incompatible, or unverified packages. Personal access tokens or credentials are never exposed in diffs or proposals. Secret scanner confirms zero leaks (PASS 0 findings). Human approval gate strictly guards workspace mutations.
- **QA Lens:** Pass. Added 59 automated unit and integration tests across 6 test modules (including 19 dedicated security test cases). Full test suite grew to 447 passing tests with 0 regressions. Verified edge cases: malformed JSON, traversal paths, encoded traversals, symlink escapes, downgrade attempts, duplicate lines, stale manifests, and reversible diff application.
- **UX Lens:** Pass. Proposal response provides human-readable explanations, clear dependency-level action classifications (`UPGRADE`, `RETAIN`, `REJECT_CONFLICT`), and diagnostic summaries suitable for frontend presentation in M7.
- **SRE Lens:** Pass. All CPU-bound AST and manifest operations in FastAPI routes execute via `run_in_threadpool`, preventing event loop starvation. Patch application and reversibility operate in-memory with sub-millisecond latency. Registry TTL cleanup prevents unbounded memory growth.

## Known limitations
- Standard JSON (RFC 8259) does not support comments; comments inside `package.json` are not preserved.
- Complex multi-manifest lockfile solvers (`poetry.lock`, `package-lock.json`) are out of scope for M4 as defined in G3 plan cutline.
- Host Docker daemon remains absent in this workstation environment; isolated container execution is scheduled for M5.

## Deviations
- None. All features implemented strictly within the approved G3 milestone scope, acceptance criteria, and post-acceptance security review requirements.
