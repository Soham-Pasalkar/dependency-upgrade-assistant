# Milestone report: M4 Upgrade planning and patch generation

## Summary
Milestone M4 delivers an end-to-end, deterministic upgrade planning, surgical manifest mutation, unified diff generation, and patch integrity validation pipeline. The system receives validated recommendations from M3, analyzes dependency relationships, filters by user selections, detects conflicts, and creates a structured upgrade plan. The surgical mutation engine updates Python `requirements.txt` (preserving comments, whitespace, extras, environment markers, and directives) and Node.js `package.json` (preserving 2-space indentation, unrelated metadata, and SemVer range prefixes like `^` and `~`) without ever mutating the original input manifest. Multi-point patch verification proves standard unified diff syntax, in-memory patch applicability, mathematical reversibility, and traceability to validated recommendations, while an explicit human approval gate strictly blocks workspace modification until confirmed by the user.

Following independent post-acceptance security reviews and concurrency audits, M4 incorporates comprehensive security, concurrency, and lifecycle integrity hardening:
- Strict server-controlled workspace containment (`WORKSPACE_ROOT` in `src/api/config.py`) forbidding arbitrary client-supplied absolute paths, directory traversal (`..`, encoded `%2e%2e`, backslashes), symlinks, and non-manifest targets.
- Server-managed `ProposalRegistry` with atomic proposal lifecycle state machine (`AVAILABLE`, `APPLYING`, `CONSUMED`, `ABANDONED`) and thread-safe `claim_for_application()`. Two simultaneous requests using the same valid `proposal_id` can never both apply the proposal or both return `APPLIED`; competing requests receive `PROPOSAL_ALREADY_IN_PROGRESS` or `PROPOSAL_ALREADY_CONSUMED`.
- Registry eviction protection: active `APPLYING` proposals are strictly immune to capacity and TTL eviction while their filesystem mutation is running. When registry capacity is exhausted and all entries are active claims, `RegistryCapacityExceededError` is raised deterministically instead of silently dropping in-flight claims.
- Fail-safe lifecycle management: pre-write validation or freshness failures safely release the claim (`release_application_claim()`) back to `AVAILABLE` for subsequent legitimate retry, while write-time exceptions and post-write verification errors transition to `ABANDONED` (fail-closed, strictly prohibiting replay of uncertain operations).
- Post-write verification & completion integrity: once filesystem replacement is initiated, post-write read-back, content verification, and `complete_application()` are protected in a dedicated block. Registry completion is strictly mandatory before returning `APPLIED`; if completion fails, the operation fails closed with `LIFECYCLE_ERROR` and transitions the proposal to `ABANDONED`.
- Ground-truth recommendation provenance enforcement: rejecting unverified custom target overrides, enforcing trusted validation statuses (`VALIDATED`, `FALLBACK_DETERMINISTIC`), strictly rejecting `REJECTED_HALLUCINATION`, `REJECTED_INCOMPATIBLE`, and `SKIPPED`, and validating ecosystem matching.
- Independent server patch re-validation during mutation application, manifest freshness checking against current on-disk content, atomic temporary file replacement (`fsync` + `os.replace`), post-write byte-level on-disk verification, and rigorous API success semantics (`APPLIED` returned only upon verified on-disk write; `TARGET_NOT_FOUND`, `STALE_BASE_CONTENT`, `INVALID_PATH`, `LIFECYCLE_ERROR`, or `NOT_APPLIED` on failures).

## Lens review
- **Architecture Lens:** Pass. Upstream interface boundary between M3 recommendations and M4 planning is cleanly decoupled via structured Pydantic schemas. Proposal storage is encapsulated in `ProposalRegistry` with thread-safe atomic state transitions (`AVAILABLE` -> `APPLYING` -> `CONSUMED`/`ABANDONED`) and eviction immunity for active claims. Manifest modification and patch validation are isolated domain services independent of FastAPI transport.
- **Security Lens:** Pass. Airtight workspace containment (`validate_workspace_destination`) prevents directory traversal, symlink escapes, absolute paths, and unauthorized file mutations. Proposal IDs generated server-side prevent client-side integrity forgery. Atomic proposal claiming prevents concurrent double-apply races. Active claims cannot be evicted. Candidate validation status enforcement rejects hallucinated, incompatible, or unverified packages. Personal access tokens or credentials are never exposed in diffs or proposals. Secret scanner confirms zero leaks (PASS 0 findings). Human approval gate strictly guards workspace mutations.
- **QA Lens:** Pass. Added 70 automated unit, integration, and concurrency tests across 7 test modules (including 19 security tests and 11 deterministic concurrency and lifecycle tests). Full test suite grew to 458 passing tests with 0 regressions. Verified edge cases: active claim eviction protection, registry capacity exhaustion, completion failure fail-closed handling, post-write read-back crash handling, concurrent write races, pre-write claim release on stale content, fail-closed behavior on I/O error, malformed JSON, traversal paths, encoded traversals, symlink escapes, downgrade attempts, and reversible diff application.
- **UX Lens:** Pass. Proposal response provides human-readable explanations, clear dependency-level action classifications (`UPGRADE`, `RETAIN`, `REJECT_CONFLICT`), and diagnostic summaries suitable for frontend presentation in M7.
- **SRE Lens:** Pass. All CPU-bound AST and manifest operations in FastAPI routes execute via `run_in_threadpool`, preventing event loop starvation. Patch application and reversibility operate in-memory with sub-millisecond latency. Registry TTL cleanup prevents unbounded memory growth while guaranteeing active claim safety. Concurrency locking is granular and bounded.

## Known limitations
- Standard JSON (RFC 8259) does not support comments; comments inside `package.json` are not preserved.
- Complex multi-manifest lockfile solvers (`poetry.lock`, `package-lock.json`) are out of scope for M4 as defined in G3 plan cutline.
- Host Docker daemon remains absent in this workstation environment; isolated container execution is scheduled for M5.
- Trust boundary note: The current workspace mutation security model assumes a single-tenant or container-isolated execution environment where concurrent local filesystem actors do not have write access to the workspace directory structure. Mitigations against sub-millisecond local symlink-swap race conditions (TOCTOU) between resolution and file replacement rely on workspace boundary containment and filesystem permissions rather than kernel-level `openat(O_NOFOLLOW)` descriptor trees.
