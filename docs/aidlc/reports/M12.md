# Milestone report: M12 Python Dependency Compatibility & Resolution Engine


## Summary
**In progress — not submitted.** Construction follows phases P1–P11 (milestone-plan.md, Revision 4).
Completed so far: P1 (data models, additive schema migration, resolver settings with ceilings) and P2
(supervisor input classification, per-role fingerprints). No resolver, proxy, job runner, enforcement,
API or UI exists yet, so no compatibility result can be produced and no acceptance criterion is complete.

Criterion status uses: Not started / Partially implemented / Implemented / Locally verified /
CI verified / Submitted / Owner approved. "Locally verified" means the tests named in the evidence
column passed on the development machine (macOS arm64, no Docker).

## Changes
### P1 and P2 (2026-11-12)
- `src/resolution/models.py` (new): resolution status, role, job status, unsupported reasons, report, resolved package, upload date, comparison models.
- `src/resolution/policy.py` (new): fixed pip policy arguments, target, allow-list version, version policy, FR-32a disclosure text.
- `src/resolution/python_input.py` (new): supervisor-side classification; only plain requirement lines, `--hash` and repository-contained `-c` files are accepted; every other construct is UNSUPPORTED with a reason and line number.
- `src/resolution/fingerprint.py` (new): per-role canonical fingerprints (ADR-011), common digest for the FR-32b comparison precondition, pinned-image environment that fails closed.
- `src/services/run_store.py`: additive tables `dua_jobs` (partial unique index: one active job per plan) and `dua_resolutions` (role column), column `dua_approvals.resolution_fingerprint`; compare-and-set job transitions with a column allow-list; atomic SUCCEEDED + proposed evidence; restart interruption without evidence. Existing tables and rows are unchanged.
- `src/api/config.py`: `RESOLVER_*` settings with NFR-13 defaults and hard ceilings enforced by settings validation.
- Tests (new): `test_resolution_config.py`, `test_resolution_store.py`, `test_resolution_migration.py`, `test_resolution_input.py`, `test_resolution_fingerprint.py`.

## Lens review
- P1/P2 (security): `packaging` accepts `requests===` (empty arbitrary equality); the classifier deliberately accepts exactly what pip's own parser accepts and lets pip reject it during resolution. No security impact: the line cannot reference a URL, path, index or file.
- P1/P2 (QA): the migration test lives in `tests/test_resolution_migration.py` to match the evidence named by criterion 13.

## Known limitations
- In progress. Docker is not installed on the development machine; every Docker-required criterion will be verified only in CI.
- The Docker host architecture is a fingerprint input supplied by the runtime (P5); enforcement (P7) will take it from the supervisor-written evidence.

## Deviations
- P1 includes the job and evidence storage primitives (compare-and-set transitions, atomic success with evidence, restart interruption). They belong to the data layer and are needed for P6's guarantees; the job runner itself (pool, runs, deadlines, cancel watcher) remains P6. No acceptance criterion or requirement changed.
