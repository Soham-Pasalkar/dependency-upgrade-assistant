# Milestone report: M12 Python Dependency Compatibility & Resolution Engine

## Summary
**Construction complete (P1–P11); not yet submitted for G4.** Python upgrade plans are resolved by pip's
own resolver inside an isolated, digest-pinned container reachable only through a per-job allow-listing
egress proxy. A trusted supervisor verifies every result against PyPI before it becomes evidence. Each
check runs the original and the proposed manifest sequentially, stores separate fingerprinted evidence,
and reports the packages the upgrade introduces with exact-file upload dates. Approval, validation,
apply and export require current, verified COMPATIBLE evidence for the proposed set; nothing else passes.
A compatibility panel in the plan stage shows honest progress and results, and exports carry the
evidence, the resolved lists and the compatibility disclosure.

Criterion status uses: Not started / Partially implemented / Implemented / Locally verified / CI verified /
Submitted / Owner approved. "Locally verified" = the named tests passed on the development machine
(macOS arm64, no Docker). Docker-dependent evidence comes only from the CI Docker job.

### P3 (2026-11-12)
- `src/resolution/target.py` (new): trusted target facts for the pinned image digest (Python 3.11.18, Debian trixie / glibc 2.41, read from the image configuration on Docker Hub): PEP 508 marker environment and supported wheel tags. A different image digest fails closed.
- `src/resolution/metadata_client.py` (new): the supervisor's own PyPI client. Fixed hosts only (`pypi.org`, `files.pythonhosted.org`), HTTPS, no credentials/ports/queries, redirects refused, responses size-bounded before parsing (index and JSON API 16 MB, metadata 2 MB), request timeout `min(8 s, time left before the run deadline)`; strict PEP 691 index parsing; PEP 658 metadata checked against the index-advertised hash. Reuses the hardened registry client's bounded reader.
- `src/resolution/pip_report.py` (new): strict parser for the untrusted pip report v1: exact key sets, no duplicate JSON keys, depth/size/count/length limits, wheels on `https://files.pythonhosted.org` only, wheel filename must agree with the claimed name and version, lowercase SHA-256 required, direct URL/VCS installs rejected.
- `src/resolution/closure.py` (new): closure proof from trusted data only: applicable direct requirements (with markers, extras, `--hash`), every applicable `Requires-Dist` with extras propagated, `Requires-Python`, repository constraints; missing or unrelated packages rejected; markers on host-kernel variables are unverifiable and fail closed.
- `src/resolution/verifier.py` (new): `ResolutionContext` (supervisor-held identity of a role), `build_report` (the only evidence constructor; fingerprint, inputs, image, policy and target always from the context), `check_binding` (role, proposal, inputs, image, policy, allow-list, target, fingerprint), and `verify_success` (ADR-011 steps 1-8 plus yanked and prerelease policy and upload dates).
- `src/resolution/python_resolver.py` (new): `evaluate_run`, the single entry from a finished run to evidence. Exit 0 → `verify_success`; non-zero → classification of pip's log: conflict causes (CONFLICT, or UNSUPPORTED when an involved package has source-only releases within the combined constraints), no-match (Requires-Python CONFLICT, source-only UNSUPPORTED, else RESOLUTION_FAILED). A status/exit-code invariant makes COMPATIBLE impossible without exit 0 and a verified report. Untrusted log text is sanitized and bounded.
- `src/resolution/index_analysis.py` (new): per-version view of an index for the target (compatible wheel, admitted sdist, Requires-Python exclusions, yanked).
- `src/resolution/upload_dates.py` (new): FR-32c rule: the selected file matched by filename and SHA-256; PEP 700 `upload-time`, else the per-version JSON API's matching `urls[]` entry; strict RFC 3339 parsing with explicit offset, converted to UTC; otherwise `date unavailable` with a reason.
- `src/resolution/comparison.py` (new): FR-32b comparison: available only when both records are COMPATIBLE, each is bound to its own context, and both contexts share the common fingerprint elements; introduced = proposed names − original names (PEP 503). `apply_comparison` changes nothing but the comparison and the introduced flags.
- `src/resolution/models.py`: `UploadDate.filename`, `ResolvedPackage.constraints` (FR-27b "selected versions and their constraints"), `ResolutionReport.failure`.
- Fixtures (new): `tests/fixtures/resolution/` — real pip reports and logs captured with `capture_fixtures.py` (pip 26.2.2, target emulation for CPython 3.11.18 manylinux x86_64, 2026-11-12; command lines in `CAPTURE.json`) and real PyPI responses trimmed to the versions the tests need; `tests/resolution_fixtures.py` serves them through the real client.

## Lens review
- P1/P2 (security): `packaging` accepts `requests===` (empty arbitrary equality); the classifier deliberately accepts exactly what pip's own parser accepts and lets pip reject it during resolution. No security impact: the line cannot reference a URL, path, index or file.
- P1/P2 (QA): the migration test lives in `tests/test_resolution_migration.py` to match the evidence named by criterion 13.
- P3 (security): the resolver's stdout is parsed with exact key sets and the semantic content (`metadata`, `is_yanked`, `environment`) is never trusted; every claim is re-derived from PyPI's index and PEP 658 metadata fetched by the supervisor. A forged success for the real numpy 2.1.0 / scipy 1.10.0 conflict is refuted by scipy's own `Requires-Dist`.
- P3 (security): log text can only produce blocking statuses; `evaluate_run` raises if any path would return COMPATIBLE without exit 0 and a verified report.
- P3 (QA): the comparison's two environment checks are equivalent once binding holds (binding ties each report's recorded common digest to its context); a mutation removing either alone is not detected, removing both is (4 failures). Kept both as defence in depth, documented in code.
- P3 (QA): one test assumption was wrong (click 8.5.1 no longer depends on colorama); the marker test now uses Flask 3.0.3's real `importlib-metadata; python_version < '3.10'`.
- P4/P5 (security): the network design was verified on a real daemon before any further work (CI run 43278534136): no direct network, no DNS, host gateway, docker0, host IP and loopback unreachable from the resolver; proxy unreachable from other networks; token absent from logs.
- P6 (security): found while writing the restart test: a worker that outlived its job could still write original-role evidence. Fixed with `record_job_evidence` (insert only while RUNNING and not cancelled), with tests.
- P6 (privacy): Docker error text can contain host paths; the job stores a fixed message and the detail goes to server logs only (tested).
- P7 (QA): every enforcement point was disabled in turn; each mutation failed tests.
- P9 (UX): the app's built-in Python sample contains `-r base-requirements.txt`, which M12 classifies as UNSUPPORTED (nested requirements); the demo uses a pasted manifest. The sample was not changed.

## Known limitations
- In progress. Docker is not installed on the development machine; every Docker-required criterion will be verified only in CI.
- The Docker host architecture is a fingerprint input supplied by the runtime (P5); enforcement (P7) will take it from the supervisor-written evidence.
- P3 is verified only against recorded data. The recorded reports come from host pip 26.2.2 with target emulation, not from the pinned image's pip, whose version is not yet known; the parser's exact key sets will be confirmed against the real container in P10.
- Target facts (Python 3.11.18, glibc 2.41) were read from the image configuration, not from a running container; P10 must compare them with the container.
- Markers that use `platform_release` or `platform_version` cannot be verified by the supervisor and fail closed (RESOLUTION_FAILED), even where pip would succeed.
- Source-only detection for conflicts uses the packages named in pip's conflict causes plus the user's own specifiers; packages pip never names are not examined.
- PyPI could change between the resolver's fetch and the supervisor's; verification then fails closed (hash or file mismatch) rather than accepting.
- Live tests depend on live PyPI; a removed or yanked upstream release can break a test (seen once: numpy release candidates).
- The COMPATIBLE browser journey runs only in CI (no local Docker).
- Docker Desktop (macOS/Windows) is not verified; CI on Linux with Docker 29 is.

## Deviations
- Run contract (affects P5, recorded in P3): pip must write `--report` to a file on the container's tmpfs, with pip's own output redirected to stderr and the report file copied to stdout on exit 0. Measured on 2026-11-12: `--report -` mixes pip's progress lines into stdout, and `--quiet` (which would separate them) suppresses the "The conflict is caused by:" lines that criterion 1 requires. Stdout remains the only report channel, so ADR-009's trust boundary is unchanged; ADR-009 shows `--report -` as the command form, and this refinement is recorded here rather than by changing the approved ADR.
- P1 includes the job and evidence storage primitives (compare-and-set transitions, atomic success with evidence, restart interruption). They belong to the data layer and are needed for P6's guarantees; the job runner itself (pool, runs, deadlines, cancel watcher) remains P6. No acceptance criterion or requirement changed.
- Criterion evidence names: export tests are in `tests/test_export_resolution.py` and the timeout hierarchy test is `tests/test_job_service.py::test_timeout_hierarchy`, as the criteria name them.
