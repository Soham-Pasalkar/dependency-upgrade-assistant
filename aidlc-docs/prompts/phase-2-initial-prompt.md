# User Prompt: Phase 2 AI-Driven Development Life Cycle (AIDLC)

## Date: 2026-10-30

### Prompt Content

```text
You are working on the existing Dependency Upgrade Assistant project.

We are starting Phase 2 of this project using an AI-Driven Development Life Cycle (AIDLC) approach.

IMPORTANT:
This is an extension of an existing working application, NOT a new project.
Preserve the existing architecture, functionality, tests, documentation, and Git history.

PROJECT OBJECTIVE

Transform the existing Dependency Upgrade Assistant into an AI-powered
Repository Analysis and Improvement Platform.

The application should allow a user to submit a GitHub repository URL.
It should then clone the repository temporarily, inspect its dependencies
and source code, use Ollama for AI analysis and proposed improvements,
validate the proposed changes, and provide downloadable outputs.

APPROVED SCOPE

1. Repository acquisition:
   - Accept a GitHub repository URL.
   - Support public repositories.
   - Design an authorization mechanism for private repositories.
   - Clone the repository into a temporary workspace.
   - Do NOT fork repositories.
   - Do NOT modify the original repository.
   - Preserve the original clone as a reference.

2. Ollama integration:
   - Connect to the locally installed Ollama runtime.
   - Discover available models instead of assuming a model name.
   - Allow the user to select an installed model.
   - Use Ollama for dependency analysis, compatibility-risk explanations,
     source-code inspection, bug identification, and code improvement.
   - Use structured JSON outputs wherever practical.
   - Validate model responses before using them.

3. Dependency analysis:
   - Discover dependency manifests in the submitted repository.
   - Initially prioritize Python requirements.txt and pyproject.toml.
   - Identify outdated dependencies using reliable package metadata.
   - Use deterministic dependency resolution for compatibility checks.
   - Use Ollama to explain potential upgrade risks and breaking changes.
   - Never treat an AI recommendation as proof of compatibility.
   - Preserve the existing dependency-upgrade functionality.

4. Code analysis and improvement:
   - Inspect source files and identify potential bugs, code smells,
     maintainability issues, and security concerns.
   - Use Ollama to generate proposed improvements.
   - Apply changes only in a separate working copy.
   - Generate reviewable diffs.
   - Never blindly overwrite source files.
   - Do not execute arbitrary commands generated by the model.

5. Automated validation:
   - Run project tests where safely supported.
   - Run code-quality checks such as Ruff where applicable.
   - Add security checks where appropriate.
   - Execute untrusted repository code only inside an isolated,
     restricted environment.
   - Capture command output, exit codes, and test results.
   - Distinguish failed tests from tests that could not be run.

6. Final delivery:
   - Generate a downloadable unified .patch file.
   - Generate a downloadable improved-project .zip file.
   - Generate a detailed analysis report.
   - Include changed files, detected issues, proposed fixes,
     dependency recommendations, and validation results.
   - Never push changes to GitHub.
   - Never create forks or pull requests.

7. One-click workflow:
   - Provide one primary button: "Analyze & Improve Repository".
   - It should orchestrate the complete workflow.
   - Display progress and individual stage statuses.
   - Handle failures without losing completed results.
   - Provide a clear final summary.

Inspect the actual workspace. The structure above is based on the current

AIDLC INSTRUCTIONS

PHASE 1: DISCOVERY AND REQUIREMENTS PLANNING ONLY.

Before proposing implementation:

1. Inspect the entire existing project.
2. Inspect the Git branch, git status, recent commits, and uncommitted changes.
3. Identify existing functionality and architectural dependencies.
4. Read the existing AIDLC documentation and approval records.
5. Run the existing test suite and record its baseline result.
6. Inspect the installed Python version and dependencies.
7. Check whether Ollama is installed and running.
8. Discover available Ollama models without downloading or installing anything.
9. Identify limitations in the current application.
10. Identify risks, security concerns, and technical constraints.

Do not modify application source code during this phase.

Create the following documents:

- plan/phase-2-implementation-plan.md
- aidlc-docs/requirements/phase-2-requirements.md
- aidlc-docs/prompts/phase-2-initial-prompt.md
- aidlc-docs/approvals/phase-2-approval-log.md

The implementation plan must include:
- Functional requirements.
- Non-functional requirements.
- Proposed architecture.
- Updated folder structure.
- Component responsibilities.
- Ollama integration design.
- Repository cloning and workspace management.
- Dependency analysis workflow.
- Code analysis and improvement workflow.
- Testing and validation strategy.
- Security considerations.
- One-click orchestration.
- Downloadable patch and ZIP generation.
- Implementation milestones.
- Risks and mitigation strategies.
- Acceptance criteria.

IMPORTANT CONSTRAINTS:

- Do not replace the existing application.
- Do not delete or rename existing files.
- Do not introduce unnecessary dependencies.
- Do not download Ollama models.
- Do not install packages.
- Do not change Git branches.
- Do not commit or push changes.
- Do not overwrite existing documentation.
- Preserve all uncommitted user changes.

When finished, provide:
1. Summary of existing project state.
2. Existing test baseline.
3. Available Ollama models and connection status.
4. Proposed architecture.
5. Updated folder structure.
6. Implementation plan.
7. Risks and unresolved decisions.

STOP after completing the planning documents.

Wait for explicit human approval before proceeding to implementation.
```
